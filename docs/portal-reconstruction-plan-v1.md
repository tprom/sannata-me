# План реконструкции портала под новый контракт (v1)

Статус: draft-for-execution
Дата: 2026-03-05
Подход: contract-first, agent-first, deterministic-render

## 1. Цель

Привести портал к единой архитектуре для 3 страниц модуля landmarks:

- главная модуля (`module-home`)
- страница города (`collection-home`)
- страница открытки достопримечательности (`item`)

через единый контракт данных, единый пайплайн сохранения форм и единый алгоритм сборки встроенного текста.

## 2. Границы v1

Входит в v1:

- единый контракт данных для `module-home`, `collection-home`, `item`
- строгая валидация входа на API-слое
- корректный merge локалей (`ru/en/de/uk`) без перезаписи соседних языков
- единый writer для файлов, которые реально читают страницы
- реконструкция формы и рендера для `collection-home`
- выравнивание формы `landmark` с реальным пайплайном страницы
- алгоритм вставки иллюстраций в текст по параметрам

Не входит в v1 (перенос в v2 при дефиците квоты):

- drag-and-drop для иллюстраций в форме
- сложные визуальные эффекты beyond базовых параметров
- массовая полировка UI/UX вне критических требований контракта

## 3. Бюджет и лимиты

Целевой бюджет: 190
Резерв: 35
Жесткий stop-loss: 210
Абсолютный потолок: 225

Правила контроля:

1. Если задача превысила лимит >30%, задача дробится и фиксируется промежуточный артефакт.
2. Не больше 1 архитектурной развилки в одной итерации.
3. После каждого этапа: green checks (types + build + smoke).

## 4. Архитектурные инварианты

1. Один канонический source-of-truth на страницу.
2. Любой agent output проходит schema validation перед записью.
3. Страницы читают только контрактные структуры, без fallback-магии, не описанной в контракте.
4. Локали не перетираются: write только по целевому языку + merge.
5. Идентификация: `cityId` (реестр) -> `slug` (роут/файлы) фиксированным mapping.

## 5. Фазы выполнения

## Фаза 0. Подготовка (без рискованных миграций)

Результат:

- frozen контракт v1.0
- таблица mapping legacy -> new
- список файлов-источников и файлов-читателей
- чеклист smoke для 3 страниц

Задачи:

1. Зафиксировать контрактные типы и JSON schema.
2. Зафиксировать алгоритм сборки встроенного текста.
3. Подготовить rollback-план на случай частичной миграции.

DoD:

- есть подписанный документ контракта
- есть список API-поинтов и writer/read-path по каждой странице
- есть smoke-сценарии (ручные + скриптовые)

## Фаза 1. Backend унификация

Результат:

- API пишет строго в реальные файлы, которые читает frontend
- merge локалей работает корректно
- форма `landmark` интегрирована с фактическим пайплайном

Задачи:

1. Валидация контрактов на API-слое.
2. Единый write-path для `collection-home`.
3. Единый write-path для `item` (отвязка от временного `landmark-data.json`).
4. Нормализация `cityId -> slug`.

DoD:

- POST всех 3 форм дает консистентные данные
- чтение страниц показывает актуальные данные без ручных правок файлов

## Фаза 2. Forms + Renderer реконструкция

Результат:

- формы соответствуют новому контракту
- рендеры не используют хрупкие line-index вставки

Задачи:

1. `collection-home` structured form под новый контракт.
2. `module-home` выравнивание структуры данных и рендера.
3. `item` рендер под расширяемый marker/inline алгоритм.

DoD:

- пользователь заполняет форму -> получает ожидаемый рендер
- рендер повторяем и детерминирован по входным данным

## Фаза 3. Миграция и стабилизация

Результат:

- legacy данные преобразованы или совместимы через migration layer
- релизный контур стабилен

Задачи:

1. dry-run миграции на выбранных городах/объектах.
2. apply миграции + report.
3. regression smoke + фиксы.

DoD:

- минимум 3 города и 3 объекта проходят полный цикл
- нет критичных расхождений между формой и страницей

## 6. Порядок спринтов

Sprint 0 (подготовительный):

- freeze контракта
- schema + validation strategy
- migration mapping

Sprint 1:

- backend writers + city mapping
- `collection-home` end-to-end

Sprint 2:

- `item` pipeline repair
- renderer alignment (`item`, `module-home`)

Sprint 3:

- миграции + стабилизация + релизный чеклист

## 7. Риски и ранние предохранители

Риск 1: двойной source-of-truth.

- Мера: явный canonical file per page + запрет скрытых fallback.

Риск 2: перезапись локалей.

- Мера: write via locale-aware merge function + тесты на 4 локали.

Риск 3: хрупкая вставка иллюстраций.

- Мера: параметризованный алгоритм (`paragraph`, `where`, `position`, `style`), а не line-index.

## 9. Definition of Success

Работа считается завершенной, когда:

- все 3 страницы рендерятся только из нового контракта
- формы сохраняют данные без ручного редактирования JSON
- встроенные иллюстрации формируются детерминированно по параметрам формы
- локализация полная (`ru/en/de/uk`) и не деградирует при повторных сохранениях
